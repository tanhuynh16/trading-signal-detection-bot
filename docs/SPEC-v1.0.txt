[Title] Signal Detection Bot
Complete Technical Specification v1.0 — Implementation-ready specification for AI coding agents
[Heading1] 1. Document Purpose
This specification defines the MVP architecture, data model, pipeline, interfaces, formulas, state machines, risk rules, scoring framework, scheduling, observability, implementation tasks, and acceptance criteria for a crypto meme/new-token Signal Detection Bot.
The intended reader is an AI coding agent (Claude Code/Cursor/Codex) or an engineer implementing the system. When this document conflicts with an implementation shortcut, this document takes precedence.
[Heading1] 2. Product Goal
Build a Base-first system that discovers newly created DEX pools, filters unsafe tokens, continuously collects measurable on-chain/market features, calculates an explainable alpha score, sends actionable Telegram alerts, and records future outcomes so strategies can be evaluated and tuned using data.
[ListBullet] Primary goal: identify potentially interesting tokens; not to predict guaranteed winners.
[ListBullet] MVP output: alert-only. No automatic trading.
[ListBullet] Execution via Maestro or direct DEX execution is explicitly out of scope for MVP.
[ListBullet] Every decision must be reproducible from stored snapshots and feature values.
[Heading1] 3. Core Principles
[ListBullet] Multi-signal, not single-signal.
[ListBullet] Risk filtering is separate from alpha scoring.
[ListBullet] Every feature must be measurable, timestamped, normalized, and backtestable.
[ListBullet] Persist raw observations and derived features whenever practical.
[ListBullet] Do not use LLMs or ML models in the critical real-time path for MVP.
[ListBullet] Use provider abstractions so data sources can be replaced without rewriting business logic.
[ListBullet] All thresholds are initial hypotheses and must be configuration-driven.
[ListBullet] The system must distinguish discovery time, event/block time, snapshot time, signal time, and outcome time.

[Heading1] 9. Provider Abstractions
Business logic must not directly depend on DexScreener, GeckoTerminal, a specific RPC vendor, or a security API.
interface PoolDiscoveryProvider {  start(onPool: (pool: TokenCandidate) => Promise<void>): Promise<void>;  stop(): Promise<void>;}interface MarketDataProvider {  getTokenMetadata(address: string): Promise<TokenMetadata>;  getPoolSnapshot(poolAddress: string): Promise<PoolSnapshot>;  getTrades(poolAddress: string, from: Date, to: Date): Promise<Trade[]>;  getPrice(poolAddress: string): Promise<PricePoint | null>;}interface SecurityProvider {  analyzeToken(tokenAddress: string, poolAddress: string): Promise<SecurityReport>;}interface BlockchainProvider {  getCode(address: string): Promise<`0x${string}`>;  simulate(call: SimulationRequest): Promise<SimulationResult>;  getBlockTimestamp(blockNumber: bigint): Promise<Date>;}
Initial implementation may use direct RPC for discovery plus one enrichment provider. External provider selection is an implementation detail behind interfaces.
[Heading1] 10. Discovery Engine
[Heading2] 10.1 Responsibilities
[ListBullet] Listen for supported pool-creation events from Uniswap and Aerodrome on Base.
[ListBullet] Convert provider-specific events to TokenCandidate.
[ListBullet] Persist discovery event before expensive analysis.
[ListBullet] Deduplicate by chain + pool address.
[ListBullet] Enqueue candidate analysis.
[Heading2] 10.2 Discovery Rules
[ListBullet] Do not use GeckoTerminal/DexScreener polling as the primary low-latency discovery mechanism.
[ListBullet] REST/indexer providers may enrich metadata and market statistics.
[ListBullet] If WebSocket disconnects, reconnect with exponential backoff and log downtime.
[ListBullet] On restart, persist last processed block and support replay with a configurable overlap window.
[Heading2] 10.3 Acceptance Criteria
[ListBullet] A newly observed supported pool creates exactly one pool record.
[ListBullet] Duplicate event delivery does not create duplicate candidates.
[ListBullet] Restarting the worker does not permanently skip blocks.
[ListBullet] A provider failure does not crash the entire worker process.
[Heading1] 11. Token Normalization
[ListBullet] Determine candidate/base token versus known quote token.
[ListBullet] Initial quote-token allowlist is configuration-driven, e.g. WETH, USDC, DAI where relevant.
[ListBullet] If neither side is a known quote token, store pool but assign lower discovery priority; do not silently delete.
[ListBullet] Persist token address as lowercase/checksummed canonical representation consistently.

[Heading1] 13. Snapshot Scheduling
For each candidate that passes minimum discovery checks, schedule snapshots at the following offsets from discovery time:
T+0, T+30s, T+1m, T+2m, T+5m, T+10m, T+30m, T+1h
[ListBullet] Use BullMQ delayed jobs or an equivalent durable scheduler.
[ListBullet] Each job is idempotent using token/pool + scheduled offset as unique identity.
[ListBullet] A snapshot job fetches data, stores raw normalized values, then may trigger feature recomputation.
[ListBullet] Tracking can stop early if token is FAIL, pool is unavailable for a configurable duration, or token reaches configured expiry.
[ListBullet] Do not recursively create unbounded jobs.
[Heading1] 14. Risk Engine
[Heading2] 14.1 Decision Model
Risk is a gate, not a positive alpha contributor.
--- TABLE ---
Flag | Initial severity | Default action
Cannot buy / invalid route | Critical | FAIL
Cannot sell / honeypot behavior | Critical | FAIL
Blacklist capability | Critical | FAIL or explicit config override
Severe trading restriction | Critical | FAIL
Owner can mint | High | WARNING
Unusual transfer tax | High | WARNING or FAIL by threshold
LP / liquidity concerns | Medium | WARNING
Extreme holder concentration | High | WARNING; optionally FAIL by config
--- END TABLE ---
The exact interpretation must be configurable and the raw security-provider response should be retained where feasible.
[Heading2] 14.2 Risk Evaluation Result
type RiskResult = {  status: RiskStatus;  riskScore: number; // 0 = safest, 100 = riskiest  flags: Array<{    code: string;    severity: 'LOW' | 'MEDIUM' | 'HIGH' | 'CRITICAL';    message: string;  }>;  evaluatedAt: Date;};
[Heading1] 15. Feature Engine
Feature calculations must be pure functions where possible: inputs are snapshots/trades/wallet data; outputs are named numeric values plus null when insufficient data exists. Do not silently substitute zero for unavailable data.
[Heading2] 15.1 Liquidity Features
--- TABLE ---
Feature | Formula / definition
liquidity_usd | Current pool liquidity in USD
liquidity_growth_5m | (current_liquidity - liquidity_5m_ago) / max(liquidity_5m_ago, epsilon)
liquidity_stability | 1 - normalized absolute change volatility across recent liquidity samples
mc_liquidity_ratio | market_cap_usd / max(liquidity_usd, epsilon)
--- END TABLE ---
[Heading2] 15.2 Momentum Features
--- TABLE ---
Feature | Formula / definition
volume_acceleration_5m | current 5m volume / average(previous three comparable 5m windows); null if history insufficient
buy_sell_ratio | buy_count / max(sell_count, 1)
trade_velocity | number of trades / window duration
unique_buyer_growth | unique buyers in current window relative to previous window
--- END TABLE ---
Example: current 5m volume = $50k; previous windows = $10k, $12k, $8k; average = $10k; acceleration = 5.0.
[Heading2] 15.3 Holder Quality Features
--- TABLE ---
Feature | Definition
holder_count | Current number of non-zero holders
holder_growth_rate | (holders_now - holders_previous) / elapsed_minutes
top10_concentration | sum of balances of top 10 holders / total supply, adjusted to exclude known LP/burn addresses where configured
holder_retention | buyers/new holders from a prior cohort still holding non-dust balance after horizon / cohort size
--- END TABLE ---
Dust threshold must be configuration-driven.
[Heading2] 15.4 Wallet Clustering Features
[ListBullet] same_funder: wallets funded by the same source.
[ListBullet] same_funding_tx: wallets receiving funds in the same transaction.
[ListBullet] similar_funding_time: configurable time proximity.
[ListBullet] similar_funding_amount: configurable percentage tolerance.
[ListBullet] cluster_concentration: percentage of tracked token holdings attributable to a detected cluster.
MVP uses deterministic heuristics. Do not introduce a graph database.
[Heading2] 15.5 Smart Money Features
MVP starts with a manually seeded wallet list plus performance metadata. Autonomous discovery is deferred.
--- TABLE ---
Metric | Definition
independent_smart_wallet_count | Count of smart wallets after clustering related wallets
smart_wallet_entry_recency | How recently smart wallets entered
smart_wallet_quality | Aggregate of wallet alpha scores
--- END TABLE ---
wallet_alpha_score =  0.20 * historical_roi_score +  0.15 * win_rate_score +  0.20 * consistency_score +  0.25 * early_entry_accuracy_score +  0.20 * recent_performance_score
This is an initial hypothesis. Scores must be versioned and recalculated without losing historical values.
[Heading1] 16. Feature Normalization
[ListBullet] Raw features must not be directly summed when scales differ.
[ListBullet] Implement reusable normalizers: min-max with clipping, log transform where appropriate, and bounded ratio scoring.
[ListBullet] Normalization parameters belong to strategy configuration and are versioned.
[ListBullet] Null feature values must be explicitly represented; scoring defines whether missing data excludes a feature or applies a neutral score.
[Heading1] 17. Alpha Scoring
Initial v1 score is explainable and deterministic.
alpha_score =  liquidity_component +  momentum_component +  holder_component +  smart_money_component  - configured_penaltiesEach component returns 0..100 before weighting.Initial weights:liquidity:   0.20momentum:    0.30holder:      0.20smartMoney:  0.30
Initial score bands:
--- TABLE ---
Score | State intent
0–39 | Ignore
40–59 | WATCHING
60–74 | INTERESTING
75–89 | STRONG_SIGNAL
90–100 | HIGH CONVICTION / still alert-only in MVP
--- END TABLE ---
All weights and thresholds are initial hypotheses, not claimed trading truths.
[Heading1] 18. Signal State Machine
NEW | risk PASS/WARNING + minimum discovery requirements vWATCHING | alpha >= interestingThreshold vINTERESTING | alpha >= strongThreshold vSTRONG_SIGNAL | +--> EXPIRED (age limit / inactivity / liquidity collapse / FAIL)Any active state --risk FAIL--> EXPIRED
[ListBullet] State transitions must be persisted.
[ListBullet] A token may upgrade but should not downgrade by default in v1 unless a configurable downgrade policy is enabled.
[ListBullet] Alert deduplication: at most one alert per level per token unless score changes by configured delta or cooldown expires.

[Heading1] 21. Outcome Tracking
For every emitted signal, store entry/reference price at signal time and evaluate fixed horizons:
1m, 5m, 15m, 30m, 1h, 4h, 24h
--- TABLE ---
Metric | Formula
return_pct | (price_horizon - signal_price) / signal_price * 100
max_runup_pct | maximum observed price between signal and horizon relative to signal price
max_drawdown_pct | minimum observed price between signal and horizon relative to signal price
--- END TABLE ---
[ListBullet] Outcome jobs must use the same durable scheduling approach as snapshots.
[ListBullet] Historical feature values and strategy version must remain immutable for reproducibility.
[Heading1] 22. Strategy Evaluation
[ListBullet] Compare outcomes by score band.
[ListBullet] Evaluate individual feature contribution and combinations.
[ListBullet] Metrics: win rate, average return, median return, return distribution, max drawdown, max runup, profit factor where trade rules exist.
[ListBullet] Do not tune strategy based only on average return; meme-token outcomes may have highly skewed distributions.
[ListBullet] Any strategy change creates a new strategyVersion.
[Heading1] 23. Queue and Failure Handling
[ListBullet] Queues: discovery-analysis, snapshot, risk-analysis, feature-calculation, notification, outcome.
[ListBullet] Jobs must be idempotent.
[ListBullet] Retry transient provider failures with exponential backoff and bounded attempts.
[ListBullet] Permanent invalid-data errors go to failed/audit storage, not infinite retry.
[ListBullet] Use correlation IDs: candidate/pool ID through the pipeline.
[ListBullet] Rate-limit external providers centrally.

[Heading1] 25. Security Requirements
[ListBullet] No private key is needed for MVP alert-only mode.
[ListBullet] Secrets must be environment variables or a secret manager, never committed.
[ListBullet] Validate all provider responses.
[ListBullet] Apply input limits to prevent oversized payload/storage abuse.
[ListBullet] Rate-limit public API calls.
[ListBullet] Execution credentials are out of scope until a dedicated execution phase.

[Heading1] 27. Global Acceptance Criteria
[ListBullet] System can run continuously on a VPS using Docker Compose.
[ListBullet] New supported pools are persisted exactly once.
[ListBullet] Every analyzed token has auditable discovery and snapshot history.
[ListBullet] Risk FAIL prevents alpha alerting.
[ListBullet] Feature values can be recomputed from stored data.
[ListBullet] Score output includes component breakdown.
[ListBullet] Signal transitions are deterministic for the same inputs/config version.
[ListBullet] Telegram alerts are deduplicated.
[ListBullet] Every alert has outcome records at configured horizons, unless provider data is unavailable and failure is recorded.
[ListBullet] Changing a strategy configuration creates a new version and does not mutate historical signal meaning.
[Heading1] 28. Explicit Non-Requirements
[ListBullet] Do not implement auto trading in this specification.
[ListBullet] Do not integrate LLM decision-making into the signal path.
[ListBullet] Do not claim that any threshold guarantees profitability.
[ListBullet] Do not build a graph database for MVP.
[ListBullet] Do not optimize for microsecond latency at the expense of data correctness.
[ListBullet] Do not add social-media ingestion before the on-chain MVP is stable.
[Heading1] 29. AI Agent Implementation Instructions
The coding agent must implement in phases and stop for review after each phase unless explicitly instructed to continue.
[ListBullet] Read this specification before modifying code.
[ListBullet] Do not invent additional major architecture components without documenting the reason.
[ListBullet] Prefer interfaces and dependency injection for providers.
[ListBullet] Write unit tests for pure feature calculations, scoring, risk decisions, and state transitions.
[ListBullet] Write integration tests for discovery deduplication, queue idempotency, and snapshot persistence.
[ListBullet] Use mocks/fixtures for external providers in tests.
[ListBullet] Do not silently choose production secrets, RPC vendors, or paid APIs.
[ListBullet] If a required provider contract is unknown, create an adapter interface and a mock implementation rather than coupling the domain logic.
[ListBullet] At the end of each phase, report changed files, tests run, known limitations, and next acceptance criteria.
